# Design

## Context

见 `proposal.md` 的 Why。技术上下文：

- 待办状态全部收敛在 `src/composables/useTodos.ts` 内：`todos` 为 `ref<Todo[]>`，`Todo` 为 `{ id: number; title: string; completed: boolean }`，`id` 由模块内的 `nextId` 自增计数器生成。
- 组件 `src/components/TodoList.vue` 只解构 `useTodos()` 的返回值，不接触任何存储 API。
- 测试栈为 `vitest` + `@vue/test-utils` + `jsdom`（`vite.config.ts` 中 `environment: 'jsdom'`）。`jsdom` 提供符合规范的 `localStorage` 实现，且在同一测试文件内跨用例共享同一个存储实例。
- 既有测试规模：`useTodos.spec.ts` 17 个用例、`TodoList.spec.ts` 13 个用例，合计 30 个。验证命令为 `npm run test:run` 与 `npm run typecheck`。
- 已归档的 `2026-09-18-add-todo-list/design.md` 把「不做持久化」「不需要 UUID」列为当时的明确取舍，并把「数据仅存在于当前会话」标注为无法用单元测试验证、只能靠「不引入持久化 API」的实现事实来保证。本次变更正是推翻了这两个前提，因此那条无法被测试的 Requirement 也随之被移除并替换为可测试的持久化行为。

## Goals / Non-Goals

**Goals:**

- 让「刷新后数据还在」这件事变成一条**可被自动化测试验证**的行为，而不是靠「代码里没写 localStorage」这种否定式事实来保证。
- 把存储的读写与降级处理全部限制在 `useTodos.ts` 内部，组件层零改动。
- 让脏数据（非法 JSON、结构不符）永远不会让页面白屏。

**Non-Goals:**

- 不做跨标签页实时同步（`storage` 事件）。一个标签页的改动不会实时推送到另一个已打开的标签页，对方在下次加载时才看到。
- 不做数据迁移 / 版本升级策略。本次是首次落盘，没有旧格式需要迁移；版本字段只作为将来迁移的锚点预留。
- 不做存储容量管理（上限、LRU、压缩）。
- 不持久化筛选状态（proposal 已明确）。

## Decisions

### 决策 1：用 `watch(todos, ..., { deep: true })` 统一落盘，而非在每个变更函数里各写一次

**做法**：在 `useTodos()` 内建立对 `todos` 的深度侦听，回调里把整份列表序列化后写入存储。`addTodo` / `toggleTodo` / `removeTodo` 保持原样，完全不感知存储。

**理由**：

- 写入点只有一处，新增任何修改 `todos` 的路径（例如将来的「编辑标题」）自动获得持久化，不会漏。
- 变更函数保持纯数据操作，逻辑层测试仍然可以在不涉及存储的前提下断言它们的行为。
- `toggleTodo` 是原地改写 `todos.value[index].completed`，`removeTodo` 是 `splice`，`addTodo` 是 `push`——三种变更方式不同，逐个打补丁容易漏掉某一种。深度侦听对三者一视同仁。

**考虑过的替代方案**：

- *在每个变更函数末尾调用 `persist()`*——写入点分散，且把存储副作用混进数据操作里；将来加修改路径时极易漏写。
- *在组件里 `watch` 并负责存储*——持久化会散到组件层，逻辑层测试测不到，与「组件零改动」的目标冲突。

**取舍**：`watch` 是异步的（默认 `flush: 'pre'`，在下一个微任务批次前触发），因此「调用 `addTodo` 后立刻读存储」在测试里拿到的是旧值。测试必须 `await nextTick()` 才能断言存储内容。这一点在 tasks 中显式标注。

### 决策 2：存储内容使用带版本号的信封结构，而非裸数组

**做法**：落盘的值为 `JSON.stringify({ version: 1, todos: Todo[] })`。

**理由**：

- 将来若要改条目结构（例如给 `Todo` 加字段、把 `id` 换成字符串），`version` 是判定「这是旧格式」的唯一依据。裸数组没有任何升级余地。
- 信封结构让「合法 JSON 但不是待办数据」这类脏值天然可判别：既要求 `version` 是已知值，也要求 `todos` 是数组。

**考虑过的替代方案**：*直接存数组*——更简单，但等于把将来的迁移成本推给未来。信封只多一层，成本可忽略。

**取舍**：存储中的内容不再能被人肉一眼读懂格式版本，需要用 `JSON.parse` 检查 `version`。可接受。

### 决策 3：读取时逐条校验，剔除非法的单个条目而非整份丢弃

**做法**：解析后对 `todos` 数组逐条判定：`title` 必须是非空字符串、`completed` 必须是布尔值、`id` 必须是数字。不合法的条目被过滤掉，合法条目保留。整个值无法解析或不是数组时，退回空列表。

**理由**：

- 逐条过滤让「一条脏数据」的爆炸半径限于它自己，而不是整份列表。用户不会因为某一条损坏就丢掉全部待办。
- 校验只检查实现真正依赖的字段，不做过度校验（例如不校验 `title` 的长度上限）——过度校验会让将来合法的数据被误杀。

**考虑过的替代方案**：*整份丢弃*——实现更简单，但一条坏数据导致全部丢失，对用户不友好。

**取舍**：校验逻辑本身需要测试覆盖，测试量略增。这是必要的成本，因为这是唯一一处「外部数据进入系统」的边界。

### 决策 4：所有存储访问包在 try/catch 中，失败即静默降级

**做法**：读和写各自包一层 `try/catch`。读失败 → 用空列表；写失败 → 忽略异常，内存中的状态照常推进。

**理由**：`localStorage` 的访问在多种情况下会抛异常而不是静默返回 `null`——隐私模式下部分浏览器、禁用 Cookie 的配置、写入超出配额。这些情况下应用必须继续可用。

**考虑过的替代方案**：*探测一次可用性、后续跳过*——需要额外的状态与一次性探测逻辑，而 try/catch 包裹本身的成本极低（正常路径无异常），不值得为省这点开销引入额外状态。

**取舍**：写入失败对用户完全不可见。这是 proposal 与 spec 都明确要求的行为（`SHALL NOT 在界面上为上述情况显示错误提示`）。

### 决策 5：`id` 生成改为从已恢复数据的最大 `id` 继续自增

**做法**：读取存储后，把 `nextId` 初始化为已恢复条目中 `id` 的最大值加一。

**理由**：如果仍从 0 开始，恢复数据后新增的待办会与已有条目 `id` 冲突，导致 `toggleTodo` / `removeTodo` 按 id 查找时命中错误的条目——这是数据正确性问题，不只是显示问题。

**考虑过的替代方案**：*改用 `crypto.randomUUID()`*——一次性解决冲突，但会改动 `Todo.id` 的类型（`number` → `string`），波及既有 17 个用例中所有用到 `id` 的断言，以及已归档 design.md 中关于「不需要 UUID」的记录。在只做持久化的变更里顺手换 id 方案属于范围蔓延。

**取舍**：保留 `number` 型 id，代价是要显式处理恢复后的计数器初始化。这个处理本身很直接（一次 `Math.max`），且它正是持久化引入的新问题，属于本次变更的份内事。

### 决策 6：存储键名与位置收敛在 `useTodos.ts` 内

**做法**：键名形如 `todo-list/todos`，作为模块级常量定义在 `useTodos.ts` 中，不导出。

**理由**：键名是实现细节，测试需要通过它构造和断言存储内容，所以在测试里重复一份字面量即可，无需导出成公共 API。将来若有多处需要写同一份数据，再抽出独立模块也不迟。

## Risks / Trade-offs

- **[风险] `jsdom` 的 `localStorage` 在同一测试文件内跨用例共享，前一个用例写入的数据渗进后一个用例，导致看似随机的失败** → 缓解：在 `useTodos.spec.ts` 与 `TodoList.spec.ts` 的 `beforeEach` 中清空存储。`TodoList.spec.ts` 尤其关键，因为组件挂载时就会读存储。

- **[风险] 深度侦听是异步的，测试若在 `addTodo` 后立即断言存储会读到旧值** → 缓解：所有针对存储内容的断言前先 `await nextTick()`（组件测试中用 `await flushPromises()` 或 `await nextTick()`）。Red 阶段会直接暴露漏 `await`。

- **[风险] 「实例隔离」用例语义反转**：原用例断言两个 `useTodos()` 互不可见；引入持久化后，同一存储下两个实例会互相看见对方的写入。**这不是 bug，而是持久化的定义** → 缓解：显式改写该用例，把它变成「两个实例共享同一份持久化数据」，并在 tasks 中标注这是刻意修改而非修复。

- **[风险] `id` 冲突若被忽略，`toggleTodo` / `removeTodo` 会静默作用到错误的条目**，表现为「点了 A 结果 B 被勾上」这种极难定位的问题 → 缓解：`useTodos.spec.ts` 中写一条专门用例——预置一条 `id` 较大的待办，恢复后新增一条，断言两条的 `id` 不同且切换/删除作用在正确的条目上。这是本次变更里最值得写的一条回归测试。

- **[风险] 写入频率**：每次勾选都整份序列化写盘。对几十条待办的规模完全无感，但若将来列表规模上到几千条，需要换成增量或防抖 → 缓解：当前不做优化，在 Non-Goals 与本节中记录该上限，避免将来被误认为「设计时没想到」。

- **[取舍] 持久化让「数据仅存在于当前会话」这条 Requirement 作废**，该条原本是已归档 design.md 中唯一承认「无法用单元测试验证」的条目。移除它换来的收益是：新行为（恢复、降级、脏数据）全部可被自动化测试覆盖，规格与测试的一致性反而提高了。

## Migration Plan

无需迁移。首次落盘，存储中没有历史格式。回滚方式为 `git revert` 对应提交：回滚后应用不再读写存储，已将数据写入本地存储的用户，其残留数据会被忽略（不做清理——若将来需要清理，应另开一个 change）。

## 测试覆盖边界（诚实记录）

本次 spec 中所有场景均可被自动化测试覆盖，但**覆盖方式是「新实例从存储恢复」，而非真正驱动浏览器刷新**。单测无法触发真实的页面重载，因此「刷新」一词在测试中由「重新调用 `useTodos()`」代为表达——这在实现上是等价的，因为刷新后组件重建、`useTodos()` 被重新调用，走的正是同一条读取路径。

各场景与用例的对应关系：

| Scenario | 覆盖用例 |
|---|---|
| 刷新后恢复待办 | `持久化到本地存储 > 从本地存储恢复待办及其完成状态` |
| 刷新后恢复完成状态 | 同上（断言 `completed` 数组为 `[true, false]`） |
| 刷新后恢复删除结果 | `持久化到本地存储 > 删除待办后同步到本地存储`（删除后存储中只剩 `B`，恢复时不会带回被删项） |
| 刷新后筛选回到全部 | `从本地存储恢复待办及其完成状态` 中 `expect(filter.value).toEqual({ kind: 'all' })` |
| 首次访问无历史数据 | `新增待办 > 初始列表为空数组` |
| 刷新后剩余未完成数量正确 | `从本地存储恢复待办及其完成状态` 中 `expect(activeCount.value).toBe(1)` |
| 存储不可用时应用仍可用 | `存储不可用时的降级 > 读取抛异常时以空列表启动` / `写入抛异常时待办仍出现在当前会话的列表中` |
| 写入失败不影响当前会话 | `存储不可用时的降级 > 写入抛异常时待办仍出现在当前会话的列表中` |
| 存储内容为非法 JSON 时以空列表启动 | `存储内容损坏时的降级 > 非法 JSON 时以空列表启动` |
| 存储内容不是数组时以空列表启动 | `存储内容损坏时的降级 > 内容是合法 JSON 但不是对象时以空列表启动` / `version 不是 1 时以空列表启动` / `todos 不是数组时以空列表启动` |
| 条目结构不合法时被丢弃 | `存储内容损坏时的降级 > 丢弃结构不合法的条目，保留合法条目` |

**未被测试直接覆盖、由实现事实保证的部分**：spec 中 `SHALL NOT 在界面上为上述情况显示错误提示` 一条，通过「降级路径没有任何错误文案或 UI 分支」这一实现事实保证——组件层完全感知不到存储，因此不存在显示提示的途径。这与已归档变更中那条「无法用单元测试验证」的 Requirement 不同：那条是行为本身无法测试，而这条是行为**由结构决定**（负向断言没有可观测的落点），因此不写针对它的断言比写一个「查找错误提示元素且断言不存在」的空断言更诚实。

## Open Questions

- 跨标签页同步（`storage` 事件）是否需要？当前明确不做，但若用户有多标签页使用习惯，可能需要后续变更。该问题不影响本次的 spec、方案与任务拆分。
